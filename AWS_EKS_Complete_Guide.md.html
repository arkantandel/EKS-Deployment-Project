Chapter 01

What is Amazon EKS?

EKS is a fully managed Kubernetes control plane that handles the complexity of cluster operations so your team can focus on building and shipping applications.

☸️
Managed Control Plane
AWS operates the Kubernetes API server, etcd, and controller manager across multiple Availability Zones — you never touch the control plane.
🔄
Automated Updates
EKS automatically patches and upgrades the Kubernetes version, ensuring you always run secure, supported releases with zero manual intervention.
🔗
Native AWS Integration
Seamless integration with IAM, VPC, Load Balancers, ECR, CloudWatch, and 200+ AWS services — your cluster is a first-class AWS citizen.
📈
Auto-Scaling
The control plane scales automatically with demand. Combine with Cluster Autoscaler and Karpenter for fully elastic worker node scaling.
🔒
Security & Compliance
SOC 2, PCI DSS, ISO 27001, HIPAA, and FedRAMP certified. IAM-native authentication via aws-iam-authenticator bridges AWS and Kubernetes RBAC.
👁️
Observability Built-in
CloudWatch Container Insights provides automatic collection of metrics, logs, and traces from your containerized applications and microservices.

Chapter 02

EKS vs. Self-Managed Kubernetes

Choose the right deployment model for your team's expertise, budget, and operational requirements.

☸️

Amazon EKS

Fully Managed Service

✓ Managed control plane — zero ops overhead
✓ Automated Kubernetes version upgrades
✓ Auto-scaling control plane on demand
✓ Native IAM, VPC, ELB, ECR integration
✓ SOC/PCI/HIPAA compliance out of the box
✓ CloudWatch monitoring built-in
✗ Higher monthly cost vs self-managed
✗ Less control over control plane config
⚙️

Self-Managed Kubernetes

DIY on EC2 Instances

✓ Cost savings with Spot + Reserved Instances
✓ Full control over all K8s configurations
✓ Access to experimental/alpha Kubernetes features
✓ AWS service integration still available
✗ Complex setup & ongoing maintenance burden
✗ Manual control plane HA and updates
✗ Scaling the control plane is challenging
✗ Security config requires extra effort
💡

Recommendation: For teams prioritizing velocity and reliability, EKS is the clear choice. Reserve self-managed Kubernetes for organizations with dedicated platform engineering teams who need extreme customization or are optimizing costs at massive scale (1000+ nodes).

Chapter 03

AWS Environment Setup

Configure identity, networking, and permissions before launching any cluster resources.

01

Create AWS Account & Enable MFA

Register at aws.amazon.com and immediately enable Multi-Factor Authentication on the root account. Never use root credentials for daily operations.

⚠️

Critical: Create a dedicated IAM admin user and lock away your root credentials after initial setup.

02

Create IAM Users & Roles

Set up IAM users with least-privilege permissions. Create an EKS cluster role and a worker node instance role with the required managed policies attached.

IAM — Required Policies
# EKS Cluster Role requires:
AmazonEKSClusterPolicy
AmazonEKSServicePolicy

# Worker Node Role requires:
AmazonEKSWorkerNodePolicy
AmazonEKS_CNI_Policy
AmazonEC2ContainerRegistryReadOnly
03

Configure AWS CLI & kubectl

Install both tools and authenticate. The AWS CLI handles AWS API calls while kubectl communicates directly with the Kubernetes API server.

BASH
# Configure AWS CLI
aws configure
# Enter: Access Key ID, Secret Key, Region, Format

# Verify AWS identity
aws sts get-caller-identity

# Install kubectl (Linux)
curl -LO "https://dl.k8s.io/release/$(curl -L -s \
  https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl && sudo mv kubectl /usr/local/bin/
04

Set Up VPC & Networking

Create a dedicated VPC with public subnets (for load balancers) and private subnets (for worker nodes), distributed across at least 2 Availability Zones.

ℹ️

Subnet Tagging: EKS requires specific tags on subnets. Public subnets need kubernetes.io/role/elb: 1 and private subnets need kubernetes.io/role/internal-elb: 1 for the load balancer controller to work correctly.

Chapter 04

Launching Your EKS Cluster

Create the cluster using the AWS CLI for repeatable, scriptable infrastructure provisioning.

05

Create the EKS Cluster

Use the AWS CLI to create your cluster. This provisions the managed control plane — typically takes 10–15 minutes to become active.

AWS CLI
aws eks create-cluster \
  --name production-cluster \
  --kubernetes-version 1.28 \
  --role-arn arn:aws:iam::ACCOUNT_ID:role/EKSClusterRole \
  --resources-vpc-config \
    subnetIds=subnet-abc,subnet-def,\
    securityGroupIds=sg-xyz,\
    endpointPrivateAccess=true,\
    endpointPublicAccess=true

# Wait for cluster to become ACTIVE
aws eks wait cluster-active --name production-cluster
06

Add Worker Node Group

Create a managed node group to provide compute capacity. EKS will automatically register nodes and join them to the cluster.

AWS CLI
aws eks create-nodegroup \
  --cluster-name production-cluster \
  --nodegroup-name main-workers \
  --node-role arn:aws:iam::ACCOUNT_ID:role/EKSNodeRole \
  --subnets subnet-abc subnet-def \
  --instance-types t3.medium \
  --scaling-config \
    minSize=2,maxSize=10,desiredSize=3 \
  --disk-size 20
07

Authenticate & Verify Cluster

Update your local kubeconfig to point kubectl at the new cluster and verify all nodes are in Ready state before deploying any workloads.

BASH
# Update kubeconfig
aws eks update-kubeconfig \
  --region us-east-1 \
  --name production-cluster

# Verify nodes are Ready
kubectl get nodes -o wide

# Check cluster info
kubectl cluster-info
Chapter 05

Deploying Applications on EKS

Package, configure, and deploy containerized applications using Docker and Kubernetes manifests.

08

Containerize with Docker

Build a production-optimized Docker image using multi-stage builds to minimize final image size, then push it to Amazon ECR.

Dockerfile
# Stage 1: Build
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production

# Stage 2: Runtime (minimal image)
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
BASH — Push to ECR
# Authenticate Docker to ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS \
  --password-stdin ACCOUNT.dkr.ecr.us-east-1.amazonaws.com

# Build, tag, and push
docker build -t my-app:latest .
docker tag my-app:latest ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/my-app:latest
docker push ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/my-app:latest
09

Write Kubernetes Deployment YAML

Define your application's desired state using a Deployment (pod management) and Service (network exposure) manifest.

YAML — deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-application
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-application
  template:
    spec:
      containers:
      - name: my-application
        image: ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/my-app:latest
        ports:
        - containerPort: 3000
        resources:
          requests:
            cpu: "250m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        readinessProbe:
          httpGet:
            path: /health
            port: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  type: LoadBalancer
  selector:
    app: my-application
  ports:
  - port: 80
    targetPort: 3000
10

Deploy & Verify Application

Apply the manifests and monitor the rolling deployment until all pods reach the Running state and the LoadBalancer endpoint becomes available.

BASH
# Deploy everything
kubectl apply -f deployment.yaml

# Watch rollout progress
kubectl rollout status deployment/my-application

# Check pods are running
kubectl get pods -l app=my-application

# Get LoadBalancer URL
kubectl get service my-app-service

# Stream live logs
kubectl logs -l app=my-application --tail=50 -f

# Scale to 5 replicas
kubectl scale deployment/my-application --replicas=5
✅

Success indicator: When kubectl get pods shows all pods with STATUS=Running and READY=1/1, your application is live and serving traffic.
